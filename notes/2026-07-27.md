# 2026-07-27 — 자동화가 처음 돌아본 날

어제 만든 것들이 실제로 처음 자동 실행됐다. **셋 다 문제를 하나씩 드러냈다.**
만들 때는 안 보이고 돌려봐야 보이는 것들이라, 이게 정상적인 순서이기도 하다.

## 1. 07:30 점검 알림이 반쪽으로 왔다

첫 자동 실행에서 이렇게 왔다.

```
📦 백업 최신 시점     ✅ ✅ ✅      ← 정상
💾 풀 상태            ❌            ← 내용 없음
🧹 마지막 스크럽                    ← 비어있음
```

수동으로 돌릴 땐 멀쩡했는데 크론에서만 깨졌다.
원인은 **cron 의 최소 `PATH`** — `/usr/bin:/bin` 뿐이라 `/usr/sbin/zpool` 을 못 찾았다.

```bash
unhealthy=$(zpool status -x 2>/dev/null)     # → 빈 문자열
if [ "$unhealthy" = "all pools are healthy" ]  # → 불일치 → ❌
```

`2>/dev/null` 로 에러를 삼키고 있어서 "명령 없음"이 "풀 이상"으로 둔갑했다.
스크립트 상단에 `PATH` 를 명시하고, **`env -i` 로 크론과 같은 빈 환경을 만들어 재현 테스트**했다.

> 어제 문서에 "오류를 삼키는 래퍼가 실패를 성공으로 위장한다"고 써놓고
> 바로 다음 날 내가 만든 스크립트에서 같은 일을 했다. 이번엔 반대 방향(정상→실패)이라
> 알아챌 수 있었을 뿐이다.

## 3. 폴백이 단일 실패점이 되어 있었다

Beszel 에서 `Connection to freebsd-dev is down` 알림.
그런데 VM 은 멀쩡히 running 이었고 prodesk 안에서는 응답했다.

```
① prodesk 무선(.109) DHCP 임대 실패 → IPv4 주소 소실
② ssh prodesk 가 .109 를 가리킴 → 접속 불가
③ freebsd-dev/freebsd 는 ProxyJump prodesk → 연쇄 실패
④ Beszel 이 VM 다운으로 보고
```

**유선(.116)은 내내 멀쩡했다.** 실제 장애가 아니라 접근 경로만 끊긴 것.

어제 유선을 주 경로로 만들면서 "ssh 별칭은 그대로 둬도 된다,
`.109` 로 붙어도 트래픽은 유선으로 나간다"고 판단했는데 — **무선이 살아 있을 때만 맞는 얘기**였다.
무선이 죽으면 목적지 주소 자체가 사라져 접속이 안 된다.

폴백용 링크를 주 별칭이 가리키고 있으면, **폴백이 오히려 단일 실패점이 된다.**

```
수정  ssh prodesk      → .116 (유선 2.5G)   주 경로
      ssh prodesk-lan  → .109 (무선)        폴백
      ebs PRODESK=     → .116
```

### 같은 뿌리가 세 군데에서 터졌다

ssh 를 고친 뒤에도 Beszel 에서 `freebsd-dev is down` → `is up` 이 반복됐다.
VM 은 21시간 42분째 무중단이었고 에이전트도 계속 떠 있었다 — **실제 장애가 아니었다.**

허브 DB 를 열어보니 prodesk 관련 셋을 전부 무선으로 등록해두고 있었다.

```
freebsd      192.168.123.109:45877
freebsd-dev  192.168.123.109:45878   ← 알림
prodesk      192.168.123.109:45876
```

VM 들은 libvirt NAT(`192.168.122.x`) 안에 있어서 prodesk 가 iptables DNAT 으로 중계한다.
그 **중계자 주소가 불안정한 무선**이었으니, 임대를 놓칠 때마다 셋이 동시에 down 됐다.

| 증상 | 실제 원인 |
|------|-----------|
| `ssh prodesk` 접속 불가 | 무선 죽음, 유선은 정상 |
| `freebsd-dev` ProxyJump 실패 | 위와 동일 (prodesk 경유) |
| Beszel VM down 알림 반복 | 위와 동일 (prodesk 중계) |

어제 "유선을 주 경로로 만들었으니 참조는 그대로 둬도 된다"고 판단했는데,
`.109` 를 물고 있던 곳이 **ssh config · ebs 백업 스크립트 · Beszel DB** 세 군데였다.

> **주소를 바꾸면 그 주소를 참조하는 곳을 전부 찾아야 한다.**
> 어제 데이터셋 이름을 바꿀 때는 `grep -rn` 으로 참조를 먼저 훑어 사고를 막았으면서,
> IP 에는 같은 절차를 적용하지 않았다. 설정 파일뿐 아니라 **애플리케이션 DB 안에 박힌 주소**도
> 참조다 — Beszel 처럼 UI 로 등록한 값은 grep 에 안 잡힌다.

## 4. 사진 1,936장이 조용히 빠져 있었다

Immich 를 띄우고 며칠 뒤 "사진이 다 안 보인다"는 걸 알아챘다.

```
디스크 미디어  64,176
Immich 자산    62,240   ← 1,936장 누락
```

확장자별로 대조해보니 `pef`·`heic`·`mov`·`png` 등은 전부 일치했고 `jpg` 와 `mp4` 만 어긋났다.
`tga`·`ini`·`db`·`zip`(315개)이 안 잡힌 건 정상 — 사진이 아니다.

누락분을 경로로 뽑아보니 **특정 디렉터리들에 통째로 몰려 있었다.**

```
783  temp_100EOSR6
517  202506_토스뱅크_플레이샵
387  11050920_성남청청페스티벌
     … 2026_유럽여행 1,609장도 0건
```

전부 **전날 `zpool/share` 를 정리하면서 `/zpool/photos` 로 합쳐진 디렉터리**였다.
Immich 스캔은 그 이전(15:00)에 돌았으니 존재를 몰랐던 것.

처음엔 디렉터리 mtime 이 2025-09, 2026-06 으로 찍혀 있어 "스캔 전부터 있던 것"으로 오판했다.
rsync·mv 가 **원본 타임스탬프를 보존**하므로 mtime 은 "언제 이 경로에 왔는지"를 말해주지 않는다.
DB 의 최상위 디렉터리 목록과 디스크를 직접 대조해서야 갈렸다.

권한·인코딩(UTF-8 정상)·제외 규칙 전부 문제없었다. 순수하게 **스캔 시점** 문제였고,
재스캔 한 번으로 64,176 = 64,176 이 됐다.

> **데이터를 옮겼으면 그것을 인덱싱하는 서비스도 갱신해야 한다.**
> 어제 IP 를 바꾸고 참조 세 곳을 놓친 것과 같은 계열이다. 파일을 옮길 때 우리는
> 파일시스템만 생각하지만, 그 위에 **자기 인덱스를 따로 들고 있는 계층**(검색엔진, 미디어
> 서버, 사진 관리자)이 있으면 거기도 참조다. 그리고 이런 누락은 에러를 내지 않는다 —
> 그냥 조용히 적게 보인다.

대응: 외부 라이브러리 자동 스캔을 `0 5 * * *` 로 건다.

## 오늘 배운 것

세 건 다 **"만든 것"과 "돌아가는 것"의 차이**에서 나왔다.

- 크론은 내 셸이 아니다 → `env -i` 로 재현
- 경보 임계는 실제 데이터로 조정해야 한다 → 정상 동작이 경고를 띄우면 임계가 틀린 것
- 접속 경로도 백업처럼 **가장 안정적인 것을 주로** 삼는다 → 폴백은 별칭으로 분리
- 파일을 옮기면 **그 위의 인덱스 계층**도 갱신 대상이다 → 조용한 누락은 에러를 안 낸다
