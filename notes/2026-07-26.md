# 2026-07-26 — 백업 대청소

`zpool` 여유 공간을 확인하려다 시작해서, 하루 종일 백업 체계를 뜯어고쳤다.
핵심은 **"백업이 있다고 믿었는데 없었던" 것들을 찾아낸 것**이다.

## 발단

`zpool`이 87%였다. ZFS는 80%를 넘으면 할당 알고리즘이 바뀌어 성능이 떨어지므로 정리에 착수.
그런데 무엇이 공간을 먹는지 보려다 이름부터 막혔다 — `rsync`, `fs1`, `fs2`.
반년 전의 내가 붙인 이름을 지금의 내가 못 읽는 상태였다.

## 찾아낸 것들

### 1. restic 백업이 15개월간 죽어 있었다

`~/work` 백업의 최신 스냅샷이 **2025-05-04**. 그동안 경보는 한 번도 없었다.

원인은 repository 주소를 **Tailscale IP로 잡아둔 것**. Tailscale이 꺼져 있으면 통째로 실패하는데,
실패가 아무 데도 보고되지 않았다. LAN IP로 바꾸자 즉시 정상 동작 — 4분 만에 88.7 GiB가 들어갔다.

### 2. 지운 1.24T가 스냅샷에 갇혀 있었다

`zpool/rsync`에서 1.24T를 지웠는데 풀 여유 공간이 **1바이트도** 늘지 않았다.
데이터가 사라진 게 아니라 회계만 `REFER` → `USEDSNAP`으로 옮겨간 것.

더 헷갈린 건 개별 스냅샷의 `USED`가 전부 `0B`로 보였다는 점. 여러 스냅샷이 공유하는 블록은
어느 하나의 `USED`에도 안 잡힌다. 12개를 **범위로** 한 번에 지우자 1.25T가 회수됐다.

### 3. 사진 백업이 원본이 아니라 축소본이었다

`~/Pictures`를 restic으로 매일 백업 중이었는데 스냅샷 크기가 **148 → 145 → 141 → 104 GiB**로
계속 줄고 있었다. 사진이 줄어들 리가 없다.

범인은 Photos의 **Optimize Mac Storage**. 디스크가 부족하면 iCloud가 로컬 원본을 축소본으로
갈아치우는데, 백업은 그 축소본을 성실히 담고 있었다. 로컬 `originals` 15,096개 vs
Parachute가 iCloud에서 받아온 백업 **271,646개** — 18배 차이.

restic `photo` 프로필을 제거하고 Parachute 쪽을 정식 경로로 삼았다.

### 4. 185G짜리 repo를 암호 분실로 폐기

`archives/orico`가 열리지 않았다. `restic.key`도 다른 후보도 전부 실패.
데이터는 멀쩡한데 복호화할 수 없으니 용량만 차지하는 쓰레기였다.

→ **키는 백업보다 중요하다.** 지금 살아있는 repo 3개가 64바이트 파일 하나를 공유한다.

### 5. 죽은 자동화 8종

인프라를 정리할 때 그것을 참조하던 자동화를 같이 정리하지 않아 생긴 것들.

| 잔재 | 원인 |
|------|------|
| `zfs-replicate-notify.sh` | bakpool 폐기 → 스냅샷 정리 로직도 멈춰 **1.25T 묶임** |
| `com.zihado.mount-zpool` | Garage 컨테이너(`.110`) 제거 후 방치 |
| `restic-gitea` (ebs) | Gitea 제거 후 방치 |
| `naverwatch` ×2 | 스크립트를 다른 디렉터리로 옮겼는데 예약은 옛 경로 |
| `restic-photo-b2` | B2 용량 상한 초과로 죽은 뒤 방치 |
| `nanoclaw` · `ebs-auto` | 실패 반복 |

`.110`의 정체는 ebs의 gitea 백업 설정을 열어보고 알았다 —
`s3:http://192.168.123.110:3900` = **Garage**(포트 3900). 위 세 개가 전부 같은 뿌리였다.

### 6. 판례 코퍼스가 이 서버에만 있었다

ebs의 `/opt/legalize/corpus` 1.9G / **23,710개가 전부 git untracked**.
git 저장소 **안에** 있었지만 원격에는 하나도 올라가 있지 않았다.
`.git`이 있다고 안심하면 안 된다 — `git status`로 확인해야 안다.

### 7. prodesk는 백업이 0이었다

`storage.md`에 "단일 vdev — 복구는 백업 의존"이라고 **내가 직접 써두고** 정작 백업이 없었다.
설계 문서에 적은 전제를 구현했는지는 별개 문제다.

### 8. 백업이 무선을 타고 있었다

prodesk가 유선(metric 100)·무선(metric 600) 둘 다 붙어 있는데 NAS 트래픽이 전부 무선이었다.
`default` metric만 보면 유선이 우선인데, **같은 서브넷은 `/24` 링크 경로가 이기고**
그게 무선에만 있었다. 고친 뒤 **938 → 2,125 Mbps**.

## 스스로 걸려 넘어진 것들

기록해 둘 값어치가 있는 오진들.

- **로그가 9일째 안 바뀌어 "죽었다"고 판단** → 스크립트가 자기 로그를 따로 쓰고 있었다. 정상이었다
- **디렉터리 mtime이 열흘 전이라 "동기화 멈춤"으로 판단** → rsync는 전송할 게 없으면 mtime도 안 바꾼다
- **`msg10p → prodesk` 375 Gbps 측정** → SSH가 즉시 실패해 `dd`가 0초에 끝난 것. 이후 측정에 전송량 검증을 붙였다
- **속도 재려고 6GB 전송을 두 번** → 과했다. 짧게 재고 넘어갔어야 했다
- **ebs 백업 스크립트를 새로 만듦** → 이미 잘 만들어둔 게 있었다. 먼저 찾아봤어야 했다

공통점은 **간접 증거로 판단한 것**. 믿을 수 있는 건 백업 도구가 보고하는 스냅샷 목록뿐이다.
