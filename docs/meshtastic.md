# Meshtastic

LoRa 메시 네트워크 노드 4대 운영 기록. 홈랩의 다른 구성과 달리 **인터넷 없이도 동작하는
독립 통신망**이고, MQTT 게이트웨이를 통해서만 기존 네트워크와 만난다.

## 구성

| 노드 | 하드웨어 | MCU | 역할 | 전원 | 접속 |
|------|----------|-----|------|------|------|
| **GM1** | Heltec V3 | ESP32-S3 | 고정 · WiFi 게이트웨이(예비) · 원격 관리 거점 | 상시전원 | TCP `192.168.123.110` |
| **GM2** | Heltec V3 | ESP32-S3 | 고정 · **MQTT 업링크 담당** | 상시전원 | TCP `192.168.123.115` |
| **W1** | Seeed Wio Tracker L1 | nRF52840 | 여행용 (OLED · 솔라 · L76K GPS) | 내장 배터리 | BLE / USB |
| **T1** | SenseCAP T1000-E | nRF52840 | 상시 휴대 (카드형 · IP65) | 내장 배터리 | BLE (아이폰) |

LoRa: 전 노드 region `KR`(920–923MHz) · LONG_FAST · hop limit 3 · TX 23dBm
라디오는 4대 모두 SX1262 계열이라 **통신 성능은 MCU와 무관**하다. 차이는 전력뿐.

## 토폴로지

```
        [msh/KR 공용 MQTT 브로커]
                  │ (mqtt.meshtastic.org:8883, TLS)
                  │ 업링크 전담
              ┌───┴───┐
              │  GM2  │ ─── WiFi ─── 홈 네트워크
              └───┬───┘                  │
                  │ RF (LoRa 920–923MHz) │
     ┌────────┬───┴────┬────────┐        │
  ┌──┴──┐  ┌──┴──┐  ┌──┴──┐  ┌──┴──┐     │
  │ GM1 │  │ W1  │  │ T1  │  │ 외부 │    │
  └──┬──┘  └─────┘  └──┬──┘  │ 노드 │    │
     └──── WiFi ───────│─────┴──────┴─────┘
                       └─ BLE ─ 아이폰

  업링크는 GM2 한 대만. 두 대가 올리면 같은 패킷이 중복 게재된다.
  GM1은 WiFi가 켜져 있지만 채널 uplink_enabled=false 라 브로커에 올리지 않는다.
```

## 실측

RF 링크 (GM1 수신 기준):

| 상대 | RSSI | SNR | 홉 |
|------|------|-----|-----|
| GM2 | -31 dBm | 6.0 dB | 0 |
| T1 | -22 dBm | 7.0 dB | 0 |
| W1 | — | 8.0 dB | 0 |
| 외부 노드 (1–2홉) | -17 ~ -20 dBm | -13 ~ 6 dB | 1–2 |

채널 이용률 3.2% · 송신 airtime 0.28%. 여유가 커서 텔레메트리를 켜도 부담 없다.

> **RSSI가 위치를 배신한다.** 노드 표의 좌표로는 GM1과 GM2가 1.8km 떨어져 보였는데
> RSSI가 -31dBm이었다. 그 거리면 -100dBm대가 나와야 한다. 좌표가 채널의
> `positionPrecision: 13` 설정 때문에 약 1.5km 격자로 뭉개져 있었던 것. 실제로는 같은 방에 있었다.
> **공개 채널에 정확한 위치를 안 뿌리는 건 옳은 설정**이지만, 그 좌표로 거리를 추정하면 안 된다.

## 업링크 · 다운링크

메시 → MQTT (업링크)는 정상 동작한다. GM1에서 텍스트를 방송하면 GM2가 수신해
`msh/KR/2/e/LongFast/!02ee8480` 토픽으로 게재하는 것을 브로커 구독으로 왕복 검증했다.

MQTT → 메시 (다운링크)는 **동작하지 않는다.** 브로커까지는 도달하지만(자기 패킷을
구독으로 되받아 확인) RF로 내려오지 않는다. 원인은 채널의 `downlink_enabled: false`.
펌웨어는 다운링크가 켜진 채널에 대해서만 MQTT 토픽을 구독하므로, 아무도 듣고 있지 않으면
RF로 내보낼 주체가 없다.

> 다운링크를 켠다면 **공개 LongFast가 아니라 별도 프라이빗 채널에만** 켤 것.
> 공개 채널에 켜면 전 세계 MQTT 트래픽이 로컬 RF로 쏟아진다.

## 교훈

### WiFi를 켜면 BLE가 꺼진다

ESP32 하드웨어 자체는 동시 사용이 가능하지만 **Meshtastic 펌웨어가 의도적으로 배타 처리**한다.
WiFi 설정이 우선권을 갖고 BLE를 비활성화한다. GM1의 WiFi를 켠 뒤 BLE 스캔을 돌리니
nRF 노드 두 대(W1·T1)만 잡히고 ESP32 노드 두 대는 목록에서 사라졌다.

잃는 것은 폰 앱 직결, 얻는 것은 **TCP API(4403)** — USB 없이 어느 기기에서든 제어할 수 있다.
고정 노드라면 명백히 이득이다.

### TCP 원격 쓰기는 조용히 실패한다

가장 비싼 교훈. GM2 이름 변경을 시도했는데 세 번 실패했다.

1. `BrokenPipeError` — 소켓이 끊겨 쓰기 자체가 안 됨 (재부팅으로 해소)
2. 같은 오류 반복
3. **오류 없이 "성공" 출력. 그런데 실제로는 반영되지 않음**

3번이 위험하다. CLI가 admin 메시지를 보낸 직후 소켓을 닫아서 기기가 플래시에 커밋하기 전에
세션이 끊긴다. 결국 TCP 세션을 15초 유지하는 스크립트로 해결했다.

```python
iface = meshtastic.tcp_interface.TCPInterface(hostname=HOST)
iface.localNode.setOwner(long_name="GM2", short_name="GM2")
time.sleep(15)          # 커밋 대기 — 이게 없으면 조용히 유실된다
iface.close()
```

> 같은 세션 안에서 `getMyUser()`로 검증하면 **캐시된 옛 값**이 나온다.
> 반드시 **새 연결로 재확인**할 것. 시리얼 쓰기에는 이 문제가 없다.

### batteryLevel 101은 "배터리 없음"이 아니다 (오진)

GM1·GM2가 `batteryLevel: 101`, 전압 4.34V로 보고하길래 "리튬 만충 4.2V를 넘으니 배터리가
없고 USB 레일 전압이다"라고 판단했다. **틀렸다.**

- `101`은 **AC/USB 외부 전원으로 구동 중**임을 나타내는 펌웨어 관례값이다. 배터리 유무와 무관하다.
- Heltec V3는 배터리 전압 ADC가 부정확한 것으로 유명하다. 그래서 `adcMultiplierOverride`
  보정 설정이 따로 있다 (기본 `0.0` = 미보정).

두 노드 모두 배터리가 달려 있었다. **텔레메트리 숫자로 하드웨어 구성을 추론하지 말 것.**
눈으로 확인하는 쪽이 항상 옳다.

### 전력은 MCU가 가른다

nRF52840은 슬립 시 수 µA, ESP32는 최적화해도 30–191µA대. 활성 상태 차이는 더 크다.
체감으로 ESP32 기기가 기본 모드 십수 시간 / Light Sleep 100시간대인 반면 nRF52는
기본 모드로도 수백 시간이 나온다.

다만 **ESP32가 배터리 구동을 못 하는 게 아니라**, 배터리만으로 오래 못 가니 고정 노드는
상시전원이 실용적인 것이다. 큰 배터리 + 솔라로 산 위 중계기를 돌리는 사례는 흔하다.
GM1은 WiFi까지 켰으니 이제 완전한 상시전원 노드다.

### 해외에서 region을 안 바꾸면 벽돌이다

법보다 실용이 먼저다. 영국·유럽 메시는 **EU_868(869.4–869.65MHz)**를 쓴다.
KR 설정(920–923MHz)으로는 50MHz 넘게 떨어져 있어 **현지 노드와 단 한 대도 통신되지 않는다.**
리스크만 지고 얻는 게 0이다.

그리고 하필 그 대역이 나쁘다. **921–925MHz는 유럽 철도 통신(GSM-R)에 할당**되어 있고,
CEPT는 2020년 이를 919.4–925.0MHz(RMR)로 확장했다. KR 대역이 통째로 그 안에 들어간다.
빈 주파수가 아니라 열차 안전 통신 대역이다.

```
meshtastic --set lora.region EU_868    # 출국 전
meshtastic --set lora.region KR        # 귀국 후
```

EU_868은 **duty cycle 10% 제한**이 있어 한도에 닿으면 펌웨어가 송신을 멈춘다. 고장이 아니다.

## 보안 메모

현재 채널이 공개 LongFast 하나뿐이고 **PSK가 기본값(`AQ==`)**이다. 이 키는 공개된 값이라
사실상 평문이다. 내부 4대끼리 주고받을 내용이 생기면 별도 암호화 채널을 파야 한다.

```
meshtastic --ch-add private
```

1:1 DM은 `hasPKC: true`라 이미 종단간 암호화된다.

## 운영 메모

- **IP 고정 필요.** GM1·GM2 모두 DHCP다. mDNS는 두 기기가 똑같이 `Meshtastic`으로 광고해서
  `meshtastic.local`이 한 대로만 잡힌다. 라우터에서 MAC 예약으로 걸 것
  (GM1 `3c:0f:02:ec:4d:08`, GM2 `3c:0f:02:ee:84:80`).
- **BLE 광고 이름은 노드 ID에서 자동 생성**된다 (`Meshtastic_3035` = `!e2cb3035`).
  노드 이름을 바꿔도 따라오지 않는다. 정상이다.
- **W1 펌웨어가 구버전**(2.7.15). GM1·GM2는 2.7.26. 여행 전 맞출 것.
- **GM2를 이설한다면** 새 위치의 WiFi를 먼저 확인할 것. WiFi가 없으면 업링크가 끊기므로
  GM1의 uplink를 켜고 GM2 것을 끄는 순서로 역할을 넘겨야 한다.

```
# 원격 조회 (읽기는 안전)
meshtastic --host 192.168.123.110 --info
meshtastic --host 192.168.123.115 --nodes

# 시리얼 (기기가 여러 대면 --port 명시)
meshtastic --port /dev/cu.usbmodem2101 --info
```

## 미해결

- GM1을 전원 교체할 때 재부팅이 발생했다(uptime 리셋). 배터리가 정상 연결되어 있었다면
  꺼지지 않았어야 한다. 커넥터 접촉 또는 방전 여부 확인 필요.
- 고정 노드 2대가 사실상 같은 위치에 있어 커버리지 이득이 없다. GM2를 다른 건물이나
  높은 곳으로 이설하는 것이 이 메시에서 가장 효과가 큰 개선이다.
