# EBS 어학 강좌 자동화

EBS 라디오 어학 강좌를 매일 받아 듣고, 월 단위로 교재를 통째로 학습 자료화하는 파이프라인.
오디오는 방송 직후 텔레그램으로 날아오고, 전사·번역·플래시카드·단어장은 리포지터리에 쌓인다.

> 이름이 겹쳐 헷갈리기 쉬운데, 여기서 말하는 EBS는 **방송사**다.
> 홈랩의 상시 서비스 노드 `ebs`(ThinkCentre M72e)와는 다른 것이다.
> 다만 이 파이프라인을 그 노드에서 돌릴 계획이라 결국 만나긴 한다.

리포지터리: [seongilp/ebs-claude](https://github.com/seongilp/ebs-claude)

## 왜 만들었나

어학 강좌는 **매일 듣는 것**이 전부인데, 실패 지점이 사람 쪽에 몰려 있다.
앱을 열고, 오늘 회차를 찾고, 놓친 날은 다시듣기를 뒤진다. 이 세 단계가 사라지면 계속 듣게 된다.

그래서 목표를 "받아오기"가 아니라 **"아무것도 안 해도 오늘 것이 손에 와 있기"**로 잡았다.
파일을 어딘가 저장해두는 게 아니라 텔레그램으로 밀어 넣는 이유다.

## 두 갈래

소스가 둘이고 성격이 완전히 다르다.

| | 일일 AOD | 월간 교재 |
|---|---|---|
| 소스 | EBS 5분당 다시듣기 | 북동아 월간 ZIP |
| 주기 | 방송일마다 | 매월 24~26일 |
| 산출 | 오디오 (텔레그램) | 전사·번역·카드·단어장 (git) |
| 진입점 | `ebs_download.py` | `bookdonga_download.py` |

일일 쪽은 **속도**가 중요하다. 방송이 끝나면 바로 손에 있어야 한다.
월간 쪽은 **정확도**가 중요하다. 한 번 만들면 계속 참조하는 자료라 오인식이 그대로 굳는다.
그래서 같은 강좌인데도 전사 모델이 다르다 — 일일은 `tiny`, 월간 일본어는 `large-v3-turbo`.

## 일일 파이프라인

```
06:40  방송 (입트영 기준)
07:00  방송 종료
       │
07:10  1차 확인 ─┐
07:40  2차 확인  ├─ 오늘 회차가 올라왔나? (스트림 파일명의 날짜로 판별)
08:10  3차 확인  │   └ 아직이면 조용히 물러남
08:40  4차 확인 ─┘
       │
       ├─ 감지 알림 (텔레그램)
       ├─ 다운로드 → 앞 10초·뒤 20초 트림
       ├─ 완료 알림 (텔레그램)
       └─ 오디오 전송 (텔레그램)
```

**왜 30분 간격으로 네 번인가** — AOD가 방송 종료 후 정확히 언제 등록되는지 확정하지 못했다.
`Last-Modified` 헤더를 받아봤지만 8월 1일 방송 파일에 7월 30일이 찍혀 나온다(CDN이 원본 시각을
그대로 주지 않는다). 확실한 건 "09시엔 있다"뿐이라, 이른 시각부터 두드려보고 안 되면
다음 차례로 넘긴다. 전송에 성공해야 마커가 남으므로 한 번 받고 나면 나머지 시도는 즉시 스킵된다.

**왜 날짜를 확인하는가** — 다시듣기 페이지는 오늘 회차가 아직 등록되지 않았어도
**직전 회차 URL을 그대로 내려준다.** 이걸 모르고 받으면 어제 것을 오늘 것으로 알고 다시 보낸다.
다행히 AOD 파일명이 `20260801_064000_*.m4a` 꼴이라 앞 8자리로 방송일을 판별할 수 있다.
덤으로 방송 시각(`064000`)까지 알려주므로, 스케줄을 잡을 때 편성표를 찾을 필요가 없었다.

**트림** — 앞 10초 시그널과 뒤 20초 안내 멘트를 잘라낸다.
`ffmpeg -ss 10 -t <남길길이> -c copy`로 스트림 카피만 하기 때문에 재인코딩이 없다.
18MB 파일이 0.2초에 끝나고 품질 손실도 없다. 자른 뒤 5초도 안 남는 경우(방송 사고로 짧은 파일이
내려온 날)에는 자르지 않고, ffmpeg가 없거나 실패해도 원본으로 전송은 계속한다.
**트림이 전송을 막아선 안 된다** — 편의 기능이 본 기능을 인질로 잡으면 안 된다.

## 월간 파이프라인

```
북동아 월간 ZIP
  │
  ├─ 추출 → audio/<강좌>/YYYY/MM/
  ├─ 회차 번호 → 방송일로 파일명 정리
  ├─ 전사 (faster-whisper)          → transcripts/
  ├─ 번역 + 읽기 (Claude Haiku)     → 같은 .md에 끼워 넣기
  ├─ 플래시카드 추출 (Claude)       → flashcards/
  ├─ Anki 덱 빌드                   → decks/ (git 제외)
  └─ 월별 단어장                    → 일본어단어장/YYYY-MM.md
```

전사 결과는 원문만 남기지 않고 **원문 / 로마자 / 한국어를 한 줄에 끼워 넣는다.**
읽을 때 시선이 왔다 갔다 하지 않아도 되고, 플래시카드 추출도 이 줄에서 바로 뽑는다.

단어장은 회차별 카드를 월 단위로 모아 **과(=상황)별 섹션**으로 묶은 것이다.
"이번 달에 배운 단어"를 한 파일에서 훑고 싶을 때 쓴다. 새 회차가 붙을 때마다 그 달 전체를
다시 훑어 덮어쓰므로 항상 최신이다.

### 강좌별 설정

강좌마다 방송 요일과 필요한 처리가 다르다.

| 강좌 | 방송 | 전사 모델 | 비고 |
|---|---|---|---|
| 입트영 | 월~토 | tiny | 일요일 휴방 |
| 귀트영 | 월~토 | tiny | 06:20~06:40 |
| 파워 잉글리시 | 월~토 | tiny | 07:40~08:00 |
| 초급일본어 | 월·화·수 | large-v3-turbo | 번역·카드·단어장까지 |
| 중국어 | 월·화·수 | — | |

일본어만 무거운 모델을 쓰는 이유는 아래 "실전에서 걸린 것들"에 있다.

## 스케줄

| 워크플로우 | 시각(KST) | 하는 일 |
|---|---|---|
| `ebs-download` | 07:10 / 07:40 / 08:10 / 08:40 (월~토) | 일일 AOD → 텔레그램 |
| `slack-transcript` | 08:00 | 그날 전사본 → Slack |
| `bookdonga-download` | 매월 24·25·26일 | 월간 ZIP → 전 과정 |
| `ebook-monitor` | 매일 09:00 | 교재 신간 발매 감시 → 텔레그램 |

월간 워크플로우가 사흘 연속인 것은 **발매일이 유동적**이기 때문이다.
완료 마커(`.state/bookdonga/YYYY-MM.done`)를 남겨 이미 끝난 달이면 무거운 작업을 통째로 건너뛴다.
이게 없으면 이미 받은 달에 대해 매번 다시 시도하다 IP 차단을 맞고 빨간 불이 켜진다.

### cron이 밀린다

**GitHub Actions의 예약 시각은 지켜지지 않는다.** 정시(`:00`)에 요청이 몰리기 때문이다.
실행 이력 30건을 뽑아보니 `23:00 UTC` 예약이 실제로는 `23:51~00:04`에 돌고 있었다 —
**50~60분 지연.** 08시에 오라고 한 게 9시에 오고 있었다.

그래서 예약을 `:10`, `:40`처럼 정시에서 비켜 잡는다. 근본 해결은 아니고,
정확한 시각이 필요하면 self-hosted runner로 옮기는 게 맞다(그래서 옮길 예정이다).

## 실전에서 걸린 것들

문서로는 안 보이고 실제로 돌려봐야 드러난 것들. 대부분 **조용히 실패**하는 종류라 더 오래 갔다.

### VAD가 단어 낭독을 통째로 삼킨다

일본어 회차 39개를 전사했더니 5개에서 단어 목록이 **통째로 사라졌다.**
처음엔 `initial_prompt`를 의심했는데 아니었다. 범인은 **VAD(음성 구간 검출)**였다.

단어 낭독은 항목이 짧고("赤い") 사이 침묵이 길다. 기본 VAD 설정
(`min_speech_duration_ms=250`)이 이걸 발화로 인정하지 않고 버린다.
VAD를 끄자 5개 회차 모두 단어 8개가 복구됐다.

다만 **회차마다 유불리가 갈린다.** VAD를 끄면 대부분 좋아지지만, 일부 회차는 반대로
앞번호가 잘려나갔다. 그래서 두 설정을 다 돌려 단어가 더 온전한 쪽을 채택한다
(39회차 기준 끈 쪽 33 / 켠 쪽 6). VAD 파라미터를 느슨하게 푸는 절충안
(`threshold=0.3`)도 시도했지만 회차별 편차가 커서 신뢰할 수 없었다.

### 파일명 숫자가 날짜가 아니었다

받은 파일이 `초급일본어_2603_02.mp3`라 3월 2일로 보이지만, 실제로는 **2과**다.
방송일은 3월 3일. 4월분은 `2604_01`이 4월 1일이라 우연히 맞아떨어져서 더 헷갈린다.

전사 본문 첫머리에 방송이 스스로 날짜를 말해준다(`3月3日、第2課、…`).
이걸 뽑아 방송일 기준으로 재명명했다. 26개 전부 월·화·수에 떨어져 편성과 일치하는 걸로 검증했다.

### 이름 규칙이 어긋나면 조용히 멈춘다

8월분 ZIP부터 파일명 구분자가 `_`에서 `-`로 바뀌었다(`초급일본어_2608-01.mp3`).
회차 번호를 `_(\d{2})\.mp3$`로만 읽던 rename이 **매칭 0건 → 그냥 return**.
경고 한 줄 없이 넘어가서 아무도 몰랐다.

파일명이 회차 번호로 남으니, 날짜로 파일을 찾는 일일 전송이 **8월 내내 대상을 못 찾았다.**
잘못 보낸 게 아니라 **한 번도 안 보냈다.** 조용한 실패가 시끄러운 실패보다 나쁘다는
전형적인 사례라, 지금은 매칭 0건이면 경고를 남긴다.

덤으로 이때 발견한 것 — 이미 날짜로 바뀐 디렉터리를 다시 돌리면 `_03`을 "회차 3"으로 읽어
날짜를 **한 번 더 민다.** 파일명 숫자가 모두 그 달 방송일 집합에 들어가면 변환이 끝난 것으로
보고 건너뛰도록 고쳤다.

### ebook과 종이책은 호스트가 다르다

교재 신간 알림 링크가 죽어 있었다. 검색·파싱·전송은 멀쩡했고 **링크만 틀렸다.**
ebook 상품에 종이책용 URL(`product.kyobobook.co.kr/detail/{pid}`)을 쓰고 있었는데,
이 주소는 ebook ID에 대해 **HTTP 200을 주면서 본문이 0바이트다.**
상태 코드만 보면 정상으로 보이고 브라우저에서 열어야 죽은 걸 안다.
ebook은 `ebook-product.kyobobook.co.kr/dig/epd/ebook/{pid}`를 써야 한다.

### whisper는 같은 말을 매번 다르게 적는다

단어장을 만들려고 과 번호를 파싱하는데, 표기가 회차마다 달랐다 —
`第1課` / `第1日` / `第8話` / `第5か`(히라가나). 월 첫 회차는 아예 한자 숫자(`六月一日 第一課`)로 적는다.
한 표기만 보면 그 회차가 통째로 단어장에서 빠진다. 네 변형을 모두 받아들이고 나서야
78개 회차 전부에서 헤더를 뽑을 수 있었다.

**교훈** — 음성 인식 결과를 파싱할 때는 "형식이 일정하다"는 가정을 하면 안 된다.
같은 방송, 같은 모델이어도 회차마다 다르게 나온다.

## 리포지터리 구조

```
ebs_download.py         일일 AOD (감지·트림·전송)
bookdonga_download.py   월간 ZIP (추출·rename·전 과정 오케스트레이션)
transcribe.py           faster-whisper 전사 + 후처리(중복 낭독 접기, 목록 번호 정리)
translate.py            Claude 번역 + 읽기 표기
flashcard_extract.py    전사본 → 카드 노트
flashcard_deck.py       노트 → Anki .apkg
vocab_builder.py        카드 → 월별 단어장
ebook_monitor.py        교재 신간 감시
send_*.py               텔레그램 / Slack 전송

audio/ transcripts/ flashcards/ 일본어단어장/   산출물 (git 추적)
decks/                                        .apkg (git 제외, 용량)
.state/ .sent/                                완료·전송 마커
```

테스트는 9개 파일 94개. 전사 후처리와 파일명 규칙처럼 **조용히 틀리는** 부분에 몰아놨다.
위의 "실전에서 걸린 것들"은 대부분 회귀 테스트로 고정되어 있다.

## 앞으로

- **self-hosted runner로 이전** — cron 지연(50~60분)이 사라지고, 무거운 전사도
  GitHub 러너보다 빠를 여지가 있다. `ebs` 노드가 이미 상시 가동이라 자연스럽다.
- **AOD 등록 시각 확정** — 07:10 1차가 계속 성공하는지 보면 실제 등록 시각의
  상한을 좁힐 수 있다. 성공하면 더 당기고, 실패가 잦으면 시각을 조정한다.
