# Backup

## 3-2-1 원칙

- **3벌** 이상의 사본 (원본 + 로컬 서버 + 클라우드)
- **2가지** 다른 매체 (로컬 ZFS + 클라우드 오브젝트 스토리지)
- **1벌**은 오프사이트 (화재·도난·서버 전체 손실에도 생존)

## 계층 구조

성격이 다른 계층을 겹쳐서 서로 다른 종류의 사고를 막는다. 같은 데이터를 **같은 방식으로**
여러 벌 두는 건 사본만 늘 뿐 막아주는 사고의 종류가 늘지 않는다.

| 계층 | 도구 | 막아주는 사고 |
|------|------|--------------|
| 1 | **rsync** 평문 미러 | 원본 디스크 고장. 백업 도구 없이도 파일을 바로 꺼낼 수 있다 |
| 2 | **restic** 스냅샷 | 실수 삭제·덮어쓰기. 과거 시점으로 되돌린다 |
| 3 | **ZFS 스냅샷** | 미러링된 사고. `rsync --delete`가 전파한 삭제를 되돌린다 |
| 4 | **오프사이트**(S3 호환) | 화재·도난·집 단위 손실 |
| 5 | **ZFS 미러 + 월간 scrub** | 디스크 고장·비트 부패 |

> **도구를 늘리는 것과 계층을 늘리는 것은 다르다.**
> 한때 restic과 kopia로 같은 데이터를 이중 백업했다. "한쪽 repo가 손상돼도 다른 쪽이
> 산다"는 논리였지만, 실제로는 **같은 종류의 사고만 두 번 막는** 구성이었다. 대신
> 복구 절차를 두 벌 익혀야 하고, 저장 용량이 두 배로 들고, 매일 쓰기가 두 배 발생했다.
> restic으로 통일하고 그 자리를 **ZFS 스냅샷**(다른 종류의 사고를 막는 계층)으로 채웠다.

> 갔는데, msg10p의 홈은 단일 NVMe의 XFS였다. 미러도 스냅샷도 없는 곳에 백업을 쌓고
> 있었던 셈. `/zpool/backup/ebs`로 옮겨 **ZFS 미러 + 일일 스냅샷 30일** 보호를 받게 했다.

### 백업 잡 (prodesk → msg10p)

prodesk의 `data` 풀은 **단일 NVMe로 미러가 없다.** ZFS 체크섬으로 손상을 감지는 하지만
복구할 사본이 없어, 이 복제가 유일한 방어선이다.

| 시각 | 잡 | 내용 |
|------|-----|------|
| 매일 04:30 | `vm-backup.sh` | `data/vms` → `msg10p:zpool/backup/prodesk-vms` (ZFS 증분) |

VM 이미지는 파일 rsync보다 **`zfs send`가 압도적으로 낫다.** 초기 전체 전송은 112 GiB로
25분 걸렸지만, 이후 증분은 **3초**에 끝난다. 변경 블록만 가기 때문이다.

- `zfs send -p`로 보내 `compression=lz4`·`recordsize=64K` 같은 속성을 보존한다.
  VM은 랜덤 I/O라 recordsize가 성능에 직결되므로 이게 빠지면 안 된다.
- 기준점은 **원격 스냅샷 목록을 최신순으로 훑어 로컬에도 남아 있는 것**을 고른다.
  한 회차를 걸러도 다음 회차가 알아서 복구된다.
- 스냅샷은 소스 7개 / 원격 5개까지 유지. **원격을 안 지우면 매일 하나씩 무한 누적된다.**

> **`zfs send` 크기 ≠ 데이터셋 `USED`.** `data/vms`는 57.6G인데 전송량은 **112 GiB**였다.
> sparse raw 이미지의 논리 블록을 보내기 때문. 전송 시간을 잡을 때는 `zfs send -nvP`로
> 실제 크기를 먼저 확인한다.

> **실행 중인 VM의 스냅샷은 크래시 컨시스턴트다** — 전원이 갑자기 나간 것과 동등하다.
> FreeBSD는 저널링이 있어 대개 정상 부팅되지만, 완전한 정합성이 필요하면 스냅샷 직전에
> `virsh suspend`를 걸거나 게스트에서 sync 한다.

`zen` VM은 `/var/lib/libvirt/images/`(ext4 루트)에 있어 이 복제에 포함되지 않는다.

| 화재·도난 | ✗ 미보호 (iCloud 자체가 클라우드 사본 역할) |

> ### "Optimize Mac Storage"는 백업을 조용히 반쪽으로 만든다
>
> 한동안 `~/Pictures`를 restic으로 매일 백업했다. 그런데 스냅샷 크기가
> **148 GiB → 145 → 141 → 104 GiB로 계속 줄고** 있었다. 사진이 줄어들 리가 없는데.
>
> 원인은 Photos의 **Optimize Mac Storage**였다. 디스크가 부족하면 iCloud가 로컬 원본을
> 축소본으로 갈아치우는데, 백업은 그 축소본을 성실히 담고 있었다. 실제로 로컬
> `originals`는 15,096개뿐이었던 반면, Parachute가 iCloud에서 받아온 백업은
> **271,646개**였다 — 18배 차이.
>
> 즉 "매일 도는 사진 백업"이 있었지만 그건 **원본이 아니었다.** 아카이브를 지킨다면서
> 썸네일을 백업하고 있었던 셈. restic `photo` 프로필을 제거하고 Parachute 쪽을
> 정식 경로로 삼았다.
>
> **교훈**: 클라우드 동기화 폴더를 백업 소스로 삼을 때는, 그 폴더가 **실물을 담고
> 있는지 플레이스홀더인지** 먼저 확인해야 한다. 백업 크기가 시간이 지나며 줄어들면
> 그게 신호다.

## 자동화 원칙

- **스케줄**: launchd(macOS)/cron(Linux)로 새벽 시간대 자동 실행
- **알림**: 매 실행 결과를 메신저로 통보 (성공/실패/스킵), 아침에 전체 요약 1건
- **외장 드라이브**: 미연결 시 실패가 아니라 **스킵** 처리 (이동식 매체 특성)
- **검증**: 주 1회 `--checksum`으로 양쪽 재해시해 silent corruption 감지
- **소스는 상시 가동 노드에**: 오프사이트 업로드는 노트북이 아니라 **서버에서** 실행한다.
  노트북이 꺼져 있거나 외장드라이브가 빠져 있어도 돌아간다.

## 백업의 진짜 위험은 "없는 것"이 아니라 "있다고 믿는 것"

정기 점검에서 **자동 백업 하나가 15개월간 실행되지 않고 있었던 것**을 발견했다.
그동안 아무 경보도 없었다. 이 사건에서 나온 교훈들.

### 로그와 종료 코드는 백업의 증거가 아니다

세 가지 함정에 연달아 걸렸다.

| 증상 | 오판 | 실제 |
|------|------|------|
| `launchd` stdout 로그가 9일째 그대로 | "작업이 죽었다" | 스크립트가 **자기 로그를 따로** 쓰고 있었다. 정상 동작 |
| `launchctl list` 종료코드 `0` | "정상 실행" | 스케줄 자체가 **설치된 적이 없었다**. 실행이 없으니 실패도 없다 |
| 백업 대상 디렉터리 mtime이 열흘 전 | "동기화가 멈췄다" | rsync가 **전송할 게 없으면** 디렉터리 mtime도 안 바뀐다. 정상 |

공통점은 전부 **간접 증거**를 봤다는 것. 유일하게 믿을 수 있는 건 **백업 도구가 보고하는
스냅샷 목록**이다. `restic snapshots`의 최신 시각, 그게 답이다.

특히 `try ... end try`(AppleScript)나 `|| true` 같은 **오류를 삼키는 래퍼**는
실패를 성공으로 위장한다. 죽은 마운트를 가리키던 로그인 작업이 매 로그인마다 조용히
실패하면서 종료코드 0을 반환하고 있었다.

### 지운다고 공간이 도는 게 아니다

1.2T를 지웠는데 풀 여유 공간이 **1바이트도** 늘지 않았다. 스냅샷이 붙잡고 있어서
데이터가 사라진 게 아니라 회계만 `REFER`에서 `USEDSNAP`으로 옮겨간 것.

```
USED      = 이 데이터셋이 실제로 차지하는 총량
REFER     = 현재 파일들이 쓰는 양
USEDSNAP  = 스냅샷이 붙잡고 있는 양   ← 여기가 범인
```

**REFER는 줄었는데 USED가 그대로면 지운 게 스냅샷에 갇힌 것이다.**

더 헷갈리는 건 개별 스냅샷의 `USED`가 전부 `0B`로 보였다는 점. `USED`는 "이 스냅샷
**하나만** 지우면 회수되는 양"이라, 여러 스냅샷이 공유하는 블록은 어디에도 안 잡힌다.
실제로 개별 합계가 226MB인데 `USEDSNAP`은 3.3GB인 경우도 있었다(15배).

지우기 전에 **범위 dry-run**으로 확인하는 게 정확하다.

```bash
zfs destroy -nv 'pool/dataset@first%last'   # → would reclaim 1.25T
```

### 키를 잃으면 백업도 잃는다

185G짜리 restic repo가 **암호를 잃어 열리지 않는 상태**로 발견됐다. 데이터는 멀쩡히
있는데 복호화할 방법이 없으니 그냥 용량만 차지하는 쓰레기였다. 결국 폐기.

암호화 백업에서 **키는 백업 자체보다 중요하다.** 지금은 여러 repo가 키 하나를 공유하는데,
그 파일 64바이트가 사라지면 전부 복구 불능이 된다. 키는 비밀번호 관리자 등 **백업과
물리적으로 다른 곳**에 둔다.

### 중단된 백업은 유령 데이터를 남긴다

오프사이트 업로드를 중간에 취소했더니, 완성된 스냅샷이 없어서 `restic stats`는
`Total Size: 0 B`로 보고하는데 **실제 버킷에는 8.1GB의 미참조 pack이 남아** 있었다.
그냥 뒀으면 매달 조용히 과금됐을 것.

```bash
restic -r <repo> prune     # → deleting unreferenced packs: 499 files
```

repo를 옮기거나 백업을 중단했으면 **prune으로 미참조 객체를 정리**해야 한다.

### `rsync --delete`는 사고도 미러링한다

미러는 백업이 아니다. 원본에서 사진이 지워지면 다음 실행에서 사본에서도 지워진다.
랜섬웨어가 원본을 암호화하면 사본도 암호화본으로 덮인다.

`--backup-dir`로 삭제분을 보관할 수 있지만 **개별 파일 단위**라 전체 시점 복원이 안 되고,
보관 기간도 짧게 잡기 쉽다. 그래서 미러 목적지에 **ZFS 일일 스냅샷**을 건다.

사진처럼 거의 변하지 않는 데이터는 스냅샷이 **변경분만** 차지하므로 사실상 0바이트다.
비용 없이 "N일 안에만 발견하면 통째로 되돌릴 수 있는" 안전망이 생긴다.
자동 스냅샷 스크립트는 `auto-` 접두사가 붙은 것만 생성·삭제하게 해서, 수동·마이그레이션
스냅샷을 실수로 지우지 않도록 분리했다.

### 죽은 자동화는 조용히 쌓인다

한 번의 점검에서 **더 이상 동작하지 않는 예약 작업 7종**이 나왔다.

- 백업 대상 풀을 폐기했는데 복제 스크립트만 남음 → 스냅샷 정리 로직도 같이 멈춰 **1.25T가 묶임**
- 컨테이너를 걷어냈는데 그 서비스를 가리키던 작업 2종이 남음
- 스크립트를 다른 디렉터리로 옮겼는데 예약 작업은 옛 경로를 가리킴 → 30분마다 실패
- 클라우드 저장소 용량 상한 초과로 죽은 뒤 방치
- 이미 제거한 서비스의 백업 크론

대부분 **인프라를 정리할 때 그것을 참조하던 자동화를 같이 정리하지 않아서** 생겼다.
무언가를 없앨 때는 `grep -rn '<지우는 것>' /etc /usr/local ~/...`로 **참조를 먼저 훑는다.**
실제로 데이터셋 이름을 바꿀 때 이 검색이 백업 repo 경로, 공유 설정, SELinux 컨텍스트를
잡아내 사고를 막았다.

## 실전에서 부딪힌 것들

### 파일명이 백업을 깨뜨린다

- **길이 초과**: 초장문 제목 → Linux 255바이트 한계 초과 → rsync 실패.
  다운로드 시점에 제목 길이를 제한(`yt-dlp -o "%(title).150B..."`)해 원천 차단.
- **이모지**: 파일명의 이모지 → rsync의 iconv가 변환 실패 → exit 23.
  BMP 밖 문자를 다운로드 시 제거.
- **NFD/NFC**: macOS는 한글을 자모 분해(NFD)로 저장, Linux는 완성형(NFC).
  rsync `--iconv=utf-8-mac,utf-8` + 기존 파일은 `convmv`로 일괄 정규화.

### macOS 메타데이터가 파일 수를 두 배로 만든다

macOS가 남긴 AppleDouble(`._*`)과 `.DS_Store`가 실데이터와 1:1로 붙어 있으면
**파일 개수가 두 배**가 된다. 250만 개짜리 디렉터리를 옮길 때 스피닝 디스크에서
메타데이터 랜덤 I/O가 병목이 되어 초반 95MB/s가 48MB/s까지 떨어졌다.
백업 exclude에 `._*`, `.DS_Store`를 반드시 넣는다.

### 대용량 삭제는 `rm`이 아니라 데이터셋 단위로

수백만 개 파일을 `rm -rf`로 지우면 메타데이터 랜덤 I/O 때문에 몇 시간이 걸린다
(CPU 2%, 나머지는 전부 디스크 대기). **`zfs destroy`는 파일 개수와 무관하게 수 초**다.
지울 가능성이 있는 데이터는 처음부터 **별도 데이터셋**으로 만들어 두면 나중이 편하다.

같은 이유로 데이터셋 **이름 변경(`zfs rename`)도 즉시**다. 247G짜리 repo를 새 구조로
옮길 때 복사 없이 rename만으로 끝냈다. 단 이건 **같은 풀 안에서만** 가능하고,
풀이 다르면 `zfs send | zfs recv`로 실제 전송이 일어난다.

### 풀 간 이동은 `send -p`

`zfs send`에 `-p`를 붙여야 `compression`·`recordsize` 같은 데이터셋 속성이 함께 넘어간다.
안 붙이면 대상 풀의 기본값으로 떨어져서 압축률이 달라진다.

스냅샷 생성 자체는 **용량을 거의 쓰지 않는다**(메타데이터 수 KB). 용량이 필요한 건
받는 쪽뿐이므로, 소스 풀 여유가 적어도 대상 풀에 자리만 있으면 된다.

### 속도 튜닝은 병목 분리부터

백업이 느릴 때 구간별 최대치를 각각 측정해 진짜 원인만 고쳤다.

```
소스(USB) → Mac → [네트워크] → [ssh 암호화] → [서버 디스크]
  123MB/s          라인레이트     118MB/s         9.1GB/s
```

전부 정상인데 rsync 총합만 느렸다 → 범인은 **Apple 기본 openrsync**(성능 반토막).
brew rsync 절대경로로 교체 + Spotlight 인덱싱 차단 + LAN에선 델타 대신 `-W`(통째 전송)
+ 구식 zlib 대신 zstd 압축 → **54 → 107 MB/s (2×)**.

### macOS FDA는 바이너리 경로에 묶인다

`~/Downloads`·`Documents` 등은 TCC 보호 폴더라 백업 바이너리에 **Full Disk Access**가
없으면 자동 백업이 팝업에서 막힌다. 그런데 FDA는 **바이너리 경로 + cdhash**에 묶여서,
Homebrew로 업그레이드하면 경로·해시가 바뀌어 **권한이 풀린다.**

그래서 백업 전용 바이너리를 `~/.config/backup/bin/` 같은 **고정 경로에 복사(pin)** 해두고
설정이 그 경로를 쓰게 한다. 도구를 업그레이드할 때만 의도적으로 재복사한다.

## 점검 루틴

경보가 없다고 정상인 게 아니므로, 주기적으로 **결과물 기준**으로 확인한다.
아래를 `backup-healthcheck.sh`로 자동화해 매일 07:30 텔레그램으로 받는다.
문제가 있으면 제목이 `⚠️ 확인 필요 N건`, 없으면 `✅ 이상 없음`이라 한 줄로 판단된다.

**맥의 예약 작업이 죽어도 여기서 잡힌다** — 맥을 직접 들여다보지 않아도 repo 스냅샷
시각이 낡아지면 경고가 뜬다. 15개월 죽어 있던 그 백업도 이 점검이 있었다면 이틀 만에
발견됐을 것이다.

```bash
# 1. 백업 도구가 보고하는 최신 스냅샷 (유일하게 믿을 수 있는 증거)
restic -r <repo> snapshots | tail -3

# 2. 예약 작업이 실제로 등록돼 있는지 (설치 안 된 스케줄 탐지)
launchctl list | grep <label>      # macOS
systemctl list-timers --all        # Linux

# 3. 스냅샷이 공간을 붙잡고 있지 않은지
zfs list -o name,used,refer,usedsnap -r <pool>

# 4. 풀 건강 + 스크럽 이력
zpool status -x
```
