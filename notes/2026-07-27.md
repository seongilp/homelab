# 2026-07-27 — 자동화가 처음 돌아본 날

어제 만든 것들이 실제로 처음 자동 실행됐다. **셋 다 문제를 하나씩 드러냈다.**
만들 때는 안 보이고 돌려봐야 보이는 것들이라, 이게 정상적인 순서이기도 하다.

저녁에는 서비스를 터널에 붙이다가 **3일간 686번 죽고 있던 랜카드**를 찾았다.
어제 무선 탓으로 결론지은 게 절반만 맞았다는 것도 그때 알았다.

## 1. 07:30 점검 알림이 반쪽으로 왔다

첫 자동 실행에서 이렇게 왔다.

```
📦 백업 최신 시점     ✅ ✅ ✅      ← 정상
💾 풀 상태            ❌            ← 내용 없음
🧹 마지막 스크럽                    ← 비어있음
```

수동으로 돌릴 땐 멀쩡했는데 크론에서만 깨졌다.
원인은 **cron 의 최소 `PATH`** — `/usr/bin:/bin` 뿐이라 `/usr/sbin/zpool` 을 못 찾았다.

```bash
unhealthy=$(zpool status -x 2>/dev/null)     # → 빈 문자열
if [ "$unhealthy" = "all pools are healthy" ]  # → 불일치 → ❌
```

`2>/dev/null` 로 에러를 삼키고 있어서 "명령 없음"이 "풀 이상"으로 둔갑했다.
스크립트 상단에 `PATH` 를 명시하고, **`env -i` 로 크론과 같은 빈 환경을 만들어 재현 테스트**했다.

> 어제 문서에 "오류를 삼키는 래퍼가 실패를 성공으로 위장한다"고 써놓고
> 바로 다음 날 내가 만든 스크립트에서 같은 일을 했다. 이번엔 반대 방향(정상→실패)이라
> 알아챌 수 있었을 뿐이다.

## 3. 폴백이 단일 실패점이 되어 있었다

Beszel 에서 `Connection to freebsd-dev is down` 알림.
그런데 VM 은 멀쩡히 running 이었고 prodesk 안에서는 응답했다.

```
① prodesk 무선(.109) DHCP 임대 실패 → IPv4 주소 소실
② ssh prodesk 가 .109 를 가리킴 → 접속 불가
③ freebsd-dev/freebsd 는 ProxyJump prodesk → 연쇄 실패
④ Beszel 이 VM 다운으로 보고
```

**유선(.116)은 내내 멀쩡했다.** 실제 장애가 아니라 접근 경로만 끊긴 것.

어제 유선을 주 경로로 만들면서 "ssh 별칭은 그대로 둬도 된다,
`.109` 로 붙어도 트래픽은 유선으로 나간다"고 판단했는데 — **무선이 살아 있을 때만 맞는 얘기**였다.
무선이 죽으면 목적지 주소 자체가 사라져 접속이 안 된다.

폴백용 링크를 주 별칭이 가리키고 있으면, **폴백이 오히려 단일 실패점이 된다.**

```
수정  ssh prodesk      → .116 (유선 2.5G)   주 경로
      ssh prodesk-lan  → .109 (무선)        폴백
      ebs PRODESK=     → .116
```

### 같은 뿌리가 세 군데에서 터졌다

ssh 를 고친 뒤에도 Beszel 에서 `freebsd-dev is down` → `is up` 이 반복됐다.
VM 은 21시간 42분째 무중단이었고 에이전트도 계속 떠 있었다 — **실제 장애가 아니었다.**

허브 DB 를 열어보니 prodesk 관련 셋을 전부 무선으로 등록해두고 있었다.

```
freebsd      192.168.123.109:45877
freebsd-dev  192.168.123.109:45878   ← 알림
prodesk      192.168.123.109:45876
```

VM 들은 libvirt NAT(`192.168.122.x`) 안에 있어서 prodesk 가 iptables DNAT 으로 중계한다.
그 **중계자 주소가 불안정한 무선**이었으니, 임대를 놓칠 때마다 셋이 동시에 down 됐다.

| 증상 | 실제 원인 |
|------|-----------|
| `ssh prodesk` 접속 불가 | 무선 죽음, 유선은 정상 |
| `freebsd-dev` ProxyJump 실패 | 위와 동일 (prodesk 경유) |
| Beszel VM down 알림 반복 | 위와 동일 (prodesk 중계) |

어제 "유선을 주 경로로 만들었으니 참조는 그대로 둬도 된다"고 판단했는데,
`.109` 를 물고 있던 곳이 **ssh config · ebs 백업 스크립트 · Beszel DB** 세 군데였다.

> **주소를 바꾸면 그 주소를 참조하는 곳을 전부 찾아야 한다.**
> 어제 데이터셋 이름을 바꿀 때는 `grep -rn` 으로 참조를 먼저 훑어 사고를 막았으면서,
> IP 에는 같은 절차를 적용하지 않았다. 설정 파일뿐 아니라 **애플리케이션 DB 안에 박힌 주소**도
> 참조다 — Beszel 처럼 UI 로 등록한 값은 grep 에 안 잡힌다.

## 5. 어제 내린 결론이 절반만 맞았다

저녁에 Jellyfin·Pinchflat을 터널에 붙이다가 cloudflared 로그에서 이걸 봤다.

```
ERR Failed to dial a quic connection
    error="write udp …->198.41.200.53:7844: sendmsg: network is unreachable"
```

파고들었더니 **유선 USB 랜카드가 3일간 686번 버스에서 사라졌다 돌아오고 있었다.**

```
r8152-cfgselector 2-3: USB disconnect, device number 57
r8152 … : Tx status -108              ← ESHUTDOWN, 전송 중 끊김
usb 2-3: new SuperSpeed USB device number 58
r8152 … : renamed from eth0           ← 드라이버 재probe
r8152 … : carrier on                  ← 4초 뒤 복구
```

`renamed from eth0`가 결정적 단서였다. 링크만 끊긴 거면 `carrier off/on`만 남는다.
드라이버가 다시 붙었다는 건 **USB 장치가 통째로 사라졌다**는 뜻이다.

**이게 안 보이는 이유가 지독하다.** 4초 만에 복구되고, 인터페이스 이름이 `enx<MAC>` 형식이라
재열거돼도 그대로고, IP도 돌아오고, `ethtool`은 평소에 `2500Mb/s Full`로 멀쩡하다.

> 어제 `freebsd-dev is down` 헛알림을 **무선 탓으로 결론지었는데 절반만 맞았다.**
> 무선도 문제였지만 유선 어댑터도 같은 증상을 내고 있었다. 원인을 하나 찾으면
> 거기서 멈추게 된다 — 설명이 되는 순간 더 안 찾는다.

교체 판단 전에 배제한 것들. 셋 다 정상인데 재열거만 반복되면 어댑터 하드웨어다.

| 확인 | 결과 |
|------|------|
| `power/control` | `on` = autosuspend 이미 비활성 |
| `ethtool` | 2500Mb/s Full, 협상 정상 |
| `ip -s link` | RX/TX errors 0 |

교체 후 즉시 0회. 원인 확정.

### 폴백이 죽어 있었다

랜카드를 뽑는 순간 prodesk가 **완전히 고립됐다.** LAN·Tailscale·터널 전부 무응답.

무선은 `nmcli`상 `connected`, SSID도 `dododo_5g`로 정상이었는데 **IPv4 주소가 없었다.**
임대 만료 후 NM이 갱신을 포기하고 방치한 것. 그 상태에서 유선이 빠지자
NM이 **주소도 없는 무선을 기본 경로로 세웠다.**

```
policy: set 'dododo_5g' (wlp0s20f3) as default for IPv4 routing and DNS
```

`nmcli con up` 한 번으로 즉시 `.109`를 받았다. 어제 "폴백이 단일 실패점이 되어 있었다"고
써놓고, 정작 **그 폴백이 살아 있는지는 확인하지 않았다.**

> `connected`는 IPv4가 있다는 뜻이 아니다. 그리고 폴백은 **실제로 통신을 시켜봐야** 산 것인지 안다.

### 랜카드를 갈면 예약이 안 따라온다

DHCP 예약은 MAC에 묶인다. 새 어댑터는 MAC이 다르니 `.116` 예약이 무효가 되고 `.111`을 받았다.
그 주소를 참조하던 여섯 곳이 한꺼번에 끊겼다.

| 참조 | 성격 |
|---|---|
| Cloudflare 터널 ingress | 원격 SaaS 설정 |
| msg10p `/etc/exports` ×3 | 다른 서버의 접근 제어 |
| ebs 백업 스크립트 `PRODESK=` | 다른 서버의 스크립트 |
| Beszel DB `systems` 테이블 | **애플리케이션 DB 안** — grep에 안 잡힌다 |
| `~/.ssh/config` · 문서 2곳 | 로컬 |

터널은 아예 **`localhost`로 바꿨다.** cloudflared가 그 호스트 안에서 도는데 IP를 적을 이유가
없었다. **참조를 고치는 것보다 참조를 없애는 게 낫다.**

이번엔 `grep`으로 먼저 훑고 시작했다. 어제 같은 실수를 반복하진 않았는데,
**Beszel DB는 여전히 grep으로 못 찾았다** — 어제 겪어서 기억하고 있었기에 찾은 것뿐이다.

신뢰 관계가 늘지 않는다. 상세는 [prodesk.md](../docs/prodesk.md#하드웨어-이상징후-보고).

**누적이 아니라 24시간 증가분을 본다.** 누적은 늘기만 해서 악화 여부를 못 알려준다.
그리고 **보고가 26시간 이상 낡으면 그 자체로 경보**다 — 오늘처럼 주소가 바뀌어
조용히 단절되는 경우를 잡는다.

### 만들자마자 버그 셋이 나왔다

**부팅 시각이 매번 달랐다.** `date +%s - uptime`으로 구했더니 실행 시각에 따라 1~2초씩
흔들려서 매번 재부팅으로 오판하고, 증가분을 누적값으로 리셋했다. 3회 연속 실행해서 잡았다.
`/proc/stat`의 `btime`은 고정값이다. 놓쳤으면 **매일 헛경보**가 왔을 것이다.

**`source`가 값을 삼켰다.** `nvme_link=8GT/s x4`를 `.`으로 읽으니 공백 뒤 `x4`를 명령으로
실행하려 들어 변수가 비었다. 키를 지정해 읽는 방식으로 바꿨고, 남이 쓴 파일을 실행하는
위험도 같이 없앴다.

**`HOME`이 없으면 restic이 통째로 죽는다.** `env -i` 시험에서 캐시 디렉터리를 못 찾아
세 개 다 "조회 실패"가 떴다. 실제 cron은 `HOME`을 주니 진짜 고장은 아니었지만,
어제 `PATH`와 같은 이유로 못 박아뒀다.

쿠키를 물려주면 풀리지만 시도하다 멈췄다. `--cookies-from-browser`는 **유튜브 쿠키만
뽑는 게 아니라 브라우저 전체 쿠키 저장소를 읽어** 3,206줄짜리 파일을 만든다.
로그인된 모든 사이트의 세션이 거기 다 들어간다. 그걸 서버에 평문으로 두는 셈이다.

생성한 파일은 난수로 덮어쓰고 삭제했다. 하려면 최소한 **유튜브 도메인만 필터링**(23줄이면
충분했다)하고 **부계정**으로 해야 한다 — 봇 우회로 판정되면 그 계정이 밴당한다.

전부 막힌 것도 아니라 **실패율부터 관찰하기로** 했다.

## 오늘 배운 것

오전 세 건, 저녁 네 건 모두 **"만든 것"과 "돌아가는 것"의 차이**에서 나왔다.

- 크론은 내 셸이 아니다 → `env -i` 로 재현 (오늘 `HOME`까지 필요하단 걸 배웠다)
- 경보 임계는 실제 데이터로 조정해야 한다 → 정상 동작이 경고를 띄우면 임계가 틀린 것
- 접속 경로도 백업처럼 **가장 안정적인 것을 주로** 삼는다 → 폴백은 별칭으로 분리
- **폴백은 살아 있는지 확인해야 폴백이다** → `connected`가 IPv4를 뜻하지 않는다
- 파일을 옮기면 **그 위의 인덱스 계층**도 갱신 대상이다 → 조용한 누락은 에러를 안 낸다
- **원인을 하나 찾으면 거기서 멈추게 된다** → 어제 무선 탓으로 끝낸 게 절반만 맞았다
- 참조는 **고치는 것보다 없애는 게** 낫다 → 터널 ingress를 `localhost`로
- 조용히 쌓이는 카운터는 **알림에 태워야** 존재한다
